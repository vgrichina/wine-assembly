What this is

a 16-bit PC, written as a wasm generator, driven by real demos

tools/toyvm is a DOS machine. The CPU is an x86 running real-mode code, the video card is a VGA with its planes and its palette and its retrace bit, the keyboard is a BIOS queue and a port, and DOS is the interrupt vector a program lands in when it asks for a file. All of it runs in the browser, on this page: every tile in the gallery has a Run button, and pressing it starts the same emulator that took the screenshot, in the tab, with the keyboard live.

It is called a toy because it began as one — a small threaded interpreter built to measure dispatch strategies before committing the large Windows emulator next door to any of them. It stopped being a toy when the measurements needed real programs. Synthetic loops are perfectly predicted by any dispatch scheme, which is the one property real code does not have, so the benchmark had to be a corpus: __TOTAL__ demoscene productions from 1993–1995, the years when a demo was a hand-written real-mode program that talked to the hardware directly. Getting those to run meant building the machine they expected.

How it runs an instruction

decode once, then walk an array

The interpreter is not written by hand. emit.js is a generator that describes every handler once and emits the WebAssembly text for whichever dispatch shell is asked for: a shared $next with one indirect tail call, that same tail replicated into every handler, a br_table switch, or classic subroutine threading. The shipped shell is the replicated tail call. It won on every program it was measured on, by about ten percent, for a reason a microbenchmark cannot show: an indirect branch per predecessor opcode gives the branch predictor one history per pair, and real instruction streams are made of pairs.

x86 bytes are decoded exactly once into an arena of 32-bit words: a handler index, then the operand words that handler consumes. Running the program is walking that array. A store into a paragraph some compiled code came from sets a flag, and the arena for it is thrown away — nearly the whole corpus is LZEXE or PKLITE packed, so the program that eventually runs is one the depacker wrote, and an interpreter that decodes ahead of the guest has to notice that.

On top of the walk sit the optimizations the benchmarks page prices one by one: fused instruction pairs, a decoder that lives in wasm, dead flag elimination, handlers pinned to the register they reach for. Then the wait loops. A demo spends most of its dispatches not in the effect but in the loop that waits for the next frame, so the retrace poll, the keyboard poll and the tick poll are each recognised and turned inside one handler, and the VGA status port is answered from the dispatch clock itself rather than from the host. The other loop that matters is the copy: REP MOVS and REP STOS become a single memory.copy or memory.fill when their span is plain RAM, with the planar VGA window, the wrap at the segment end and code bytes all guarded.

Above the interpreter is a trace JIT. A hot trace is stitched into one wasm function with its operands folded to constants, then three whole-trace passes — constant propagation, register-file folding, dead flags — take it to about 3x the interpreter on the traces that were measured, and a region compiler installs those into the running program. What it does not yet do is register allocation: guest registers still live in wasm globals across the trace, which is the single largest item on the list.

How it runs a program

the machine is most of the work

Not one blocker in the corpus has ever been an instruction. Every program that stopped was stopped by the machine: a driver it probed for and did not find, a file it could not open, a paragraph of memory it could not get, a key nobody pressed. So the machine grew to meet them. DOS opens, reads, seeks, creates and runs files — created files live in memory, and EXEC loads a child with its own PSP and returns through a stack of parents. There is an environment block with the program's own path in it, a command tail, XMS with lockable blocks above the megabyte, EMS mapping four pages at E000, and sixteen megabytes of RAM behind an address bus that stays a 20-bit one until the guest takes an XMS handle.

The VGA knows mode 13h, the unchained and planar modes, the text pages and the CRTC start address a demo flips between them. A headless run has to answer the menus these programs open on — Do YOU have a GUS [Y/N] — so the harness reads the text screen, finds the option that means silence, and presses it, once per distinct screen. In the browser that same answerer runs until you press a key yourself.

What it does not do is protected mode. A dozen programs in the corpus are the same 32-bit DOS extender, and they stop at LGDT: descriptor tables and a 32-bit code segment are a second addressing mode for the whole machine, and they are the largest thing left. There is no sound hardware either, which is why so many of these demos are running in their own silent mode. The notes page is the record of each of those findings, in the order they were made.

How it runs in a page

the same modules, packed, on the main thread

The browser build is not a port. bundle-browser.js packs the Node modules the headless sweep uses — the decoder, the machine, the frame reader — behind a small require and an fs whose disk is a map of the demo's directory. A page-side driver runs the guest in eight-millisecond chunks per animation frame and paints whatever surface the program is on, at the guest's own resolution, so a 320x200 demo stays a 320x200 demo. The wasm tail-call proposal is probed with a thirty-byte module rather than sniffed from a version string; an engine without it gets the subroutine-threaded shell, which is four percent slower and otherwise the same machine.

Every demo ships with the site as bytes, one script per production, and only the one you press loads. Nothing here needs a server: the pages work from a file:// URL, which is why the bytes arrive as script tags and not as a fetch.

In the page the machine runs at the speed it was written for rather than as fast as the tab can go. One guest second is one wall second at the selected CPU — a 486 at ten million dispatches a second by default, and every guest clock derives from that one number: the BIOS tick, the timer interrupt at whatever rate the program reprogrammed the PIT to, the 70Hz retrace, the sample rate of a Sound Blaster transfer. Unpaced keeps those clocks and simply never waits, which is what the headless sweep does. Sound is the same samples the card would have pulled through its DMA channel, plus the PC speaker, rendered on the main thread and handed to a Web Audio node; the sound button mutes it and is remembered, and with sound off the menu answerer takes the silent option the way the sweep did. The OPL2 is still detection only — an AdLib tune is silent here for now. Full screen is the Fullscreen API where a browser has one and a viewport-sized dialog where it does not, which on a phone is the same picture with our own bar hidden.

Seven ways to run the same x86

four dispatch shells and three JIT tiers, measured on these demos

The emulator behind every screenshot on this page is a threaded interpreter: each guest instruction is decoded once into a (handler index, operand) pair, and running the program means walking that array and jumping to each handler in turn. How the jump is written is not fixed — tools/toyvm/emit.js emits the same handlers behind four different dispatch shells, and tools/toyvm/trace-jit.js can compile a hot trace out of the loop entirely. The demos in this gallery are what all seven were measured on, which is the reason to describe them here: these are not synthetic loops, they are the exact programs above.

The data structure all four walk

x86 is decoded exactly once, into an arena of 32-bit words. A decoded instruction is a handler index followed by however many operand words that handler consumes — zero for a register-to-register op that packs both registers into one word, three for a memory-destination op with a displacement and an immediate. A run of them ends in an end op carrying the guest IP the block finished at, which is where the guest's real ip gets written: once per block, not once per instruction.

 guest bytes                    arena words (4 bytes each)
 ───────────                    ──────────────────────────
                                │
 01 d8     add ax,bx           │ [ fn ] [ dst | src<<4 ]
 03 46 fc  add ax,[bp-4]       │ [ fn ] [ eaKind | seg<<4 | reg<<8 ] [ disp ]
 81 06 ..  add [..],imm        │ [ fn ] [ eaKind | seg<<4 | reg<<8 ] [ disp ] [ imm ]
 75 f8     jnz  -8             │ [ fn ] [ target ]
                                │ [ end ] [ guest ip ]
                                │
                fn = index into the handler table; order IS the index
                operands = read by the handler's own preamble

 guest CPU state lives in wasm globals  (ax bx cx .. cs ds es ss, flags,
 gip, and the arena pointer ip)  —  $t0..$t7 are per-handler scratch

fig 1 — the threaded-code arena. One decode, then every execution is a walk.

Every shell below runs the same five-step dispatch. Four of those steps are identical in all four builds; only the last one differs, and that is the entire experiment.

   steps--                          ; slice budget, so the host gets control back
   if (halt) return                 ; a handler asked to stop
   fn = i32.load [ip]               ; one word: which handler
   ip += 4                          ; step past it
   >>> branch on fn <<<             ; ← THE ONLY LINE THAT DIFFERS

 …and then, inside the handler, its operand preamble:

   $t0 = i32.load [ip + 0]           ; ops(n), generated by one function,
   $t1 = i32.load [ip + 4]           ; so every handler's shape is identical
   ip += 4 * n
   << the actual work >>

fig 2 — the dispatch sequence. That uniform preamble is also what makes the JIT's tier 1 a text substitution.

The four dispatch shells

Same decoder, same handler bodies, same guest state. The only thing that changes is the shape of the branch that gets from one handler to the next, and therefore how many distinct indirect-branch sites the CPU's predictor sees.

fig 3 — the four shells. Everything above the branch is byte-identical between them.

Why replication wins, mechanically. A branch predictor keys its history on the address of the branch. With one shared site, every add in the program competes for the same table entry as every jnz, and the target it predicts is whatever the last instruction — any instruction — happened to run. With N sites the entry for add's dispatch only ever records what follows an add, and real code is full of such pairs: a cmp is nearly always followed by a conditional jump, a push by another push. Replication costs nothing but code size, and it is the one structural idea in this comparison the synthetic microbench never tested — because a synthetic loop is perfectly predicted by any scheme, which is exactly the property real programs do not have.

Replication wins on all ten programs it was measured over, and it is the shell the synthetic microbench never tested. Giving each handler its own return_call_indirect hands the branch predictor a separate history slot per predecessor opcode — and in a real instruction stream the next opcode correlates strongly with the current one. One shared site throws that correlation away. Three independent 94-program sweeps put it at +9.7%, +9.9% and +10.5%; on the programs that draw pixels it is +11.3%, on the ones that do not, +10.0%. It is the rare change that is uniform across a corpus.

The giant br_table does not reproduce its microbench win. A synthetic benchmark claimed +46–49% for the same pair; the demos give +4.2%, and bimodally rather than merely smaller — DSTNFO.EXE +40.1%, COPPER.EXE −26.0%, reproduced across two runs at different box loads. A switch build inlines every handler body into one function, so what it costs depends on whether that program's hot handlers still fit the engine's compilation budgets. That is a property of the program, not of dispatch. calls is the least surprising line: an extra return edge per dispatch buys nothing.

Read the spread before reading any of this. Within-arm min-to-max ran 6–63% across these runs — routinely wider than the gap between two arms. The harness interleaves the arms, rotates which one starts, quotes minima and prints load average either side, because a sequential arm-then-arm layout on this box would have produced a confident number for whichever arm happened to run during a quiet minute.

The three JIT tiers

Dispatch is only the outer loop. The other question is what happens if a hot trace stops being an array walk at all and becomes one wasm function.

fig 4 — why pass 1 has to come first: folding the operand load is not folding the operand.

Tier 1 is a text substitution and needs no per-handler work: every handler's operand preamble is generated by one function and therefore has one exact shape, so the stitcher can fold it mechanically. Tier 2 needs the whole trace in view and cannot be done by a stitcher. Folding the operand load is not folding the operand — bodies read it back as a local, which keeps the register-file br_table opaque. Propagating the constant into its uses is what turns an 8-way br_table over globals into a single global access, and only then is it visible that a flag word gets overwritten before anything reads it.

Stitching is most of the distance but not the project. A 1.76x still sitting on top of it after three passes is too large to leave in a stitcher-only design — and that 1.76x is a floor, not a ceiling: tier 2 does no register allocation, so guest registers still live in globals rather than in wasm locals across the trace. That is the single biggest thing still on the table.

One result goes the other way, and it is the reason to measure on demos instead of on theory: only 3 of DRAGON.EXE's 20 flag computations were dead. In a branch-dense bit-reader the flags are genuinely live, so eager flags cost far less on that shape than the theory predicts, and FLY.EXE is a program where tier 2 came out slower than tier 1.

The 3.22x figure counts 23 distinct traces. An earlier 34-trace run read 3.31x, but that set counts one LZEXE/PKLITE bit-reader loop eight times — the same three instructions (d1 ed / 4a / 74) reached through eight different unpackers. Weighting a corpus by how many demos shipped with the same unpacker measures the packer, not the JIT.

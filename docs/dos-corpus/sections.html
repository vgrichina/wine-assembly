They were asking for DOS, not for a CPU

the blockers were all machine, none of them instructions

The work list this sweep produces is short, and not one item on it has ever been an instruction the VM could not execute. Every program in both classes below was decoding and running perfectly and stopping on something the machine did not provide — a driver, a file, a paragraph of memory, a keystroke. That distinction is invisible to an opcode census, which is the whole reason for photographing screens instead of counting bytes.

The ones that printed an error and exited

Two of those are worth the detail. A driver is mostly its detection. HIMEM.SYS NEEDED !!! is not a program failing to use extended memory, it is a program failing to find it: INT 2Fh AX=4300 went unhandled, and an unhandled multiplex call reads exactly like a machine with no driver loaded. The same for EMS, where the classic probe reads the string EMMXXXX0 out of the INT 67h handler's own segment — so the interrupt stubs had to move from offset v to 0x100 + v to make room for it. At the old layout those eight signature bytes would have landed on top of the stubs for INT 0Ah through INT 11h, INT 10h among them.

Extended memory blocks started life in host buffers, on the reasoning that a real-mode program cannot address them anyway — everything it can do with one goes through the XMS move call, so Lock failed rather than inventing a 32-bit address nothing was behind. Ten programs disagreed, all of them from the same intro system, all of them stopping on that one call with Extended memory allocation failure. (weird eh???). They lock the block, take the linear address, and write through it from real mode with a 32-bit offset.

So there is somewhere for that address to point now. Guest RAM is 16MB — the 8086's megabyte, then extended memory above the HMA — and blocks are cut from it. The address bus is the interesting part: an 8086 has twenty address lines and every address wraps at 1MB, a machine with extended memory in it does not, and a program can tell which one it is on. Address translation masks through a global that holds the 8086's twenty lines until the guest takes an XMS handle, and only then widens. A program that never asks for extended memory keeps exact 8086 wrap semantics, and the instruction gate — whose vectors are recorded off real silicon, wrap included — never notices the change.

MAINPART.EXE is the whole shape of it

It printed ERROR: Expanded Memory Manager required ! and exited. With EMS it stopped printing that, allocated a handle, mapped four pages — and drew nothing at all, for 120 million dispatches. The interrupt trace says why in one line: between the page maps sit INT 21h AH=42 and AH=3F, both marked UNHANDLED. It was reading its data into those pages and every read was going nowhere, so it rendered an empty screen out of an empty buffer — which looks like a broken decoder and is a missing read().

The ones that were waiting for a key

The harness answers a blocking key read with a synthetic keystroke, and that keystroke was Enter, always. About ten programs open on a menu that ignores Enter completely and wants one specific character, so they sat at the prompt for the entire run. A rotation through likely keys gets past that eventually, but eventually means several wrong keys first, and a menu that redraws on a bad key never settles.

The screen is right there and it says what it wants. The synthetic key now reads the menu: it scans the text page for selector · label pairs and picks the option whose label means silence, which is what a headless run wants in every one of these. The blind rotation is only the fallback. It answers once per distinct screen, because a program still showing the same menu did not accept that key, and sending it again forever is how a run hangs politely.

CULT.EXE      Do YOU have a GUS [Y/N]                         -> n
CYCLE.EXE     (G)ravis Ultra Sound / (O)thers / (N)one ???    -> N
BTW.EXE       [1] 210h … [0] Just kidding! I don't even own a GUS!!!  -> 0

BLIQ.EXE and CONTAGIO.EXE printed Can not init file manager while making no file call at all, which is what gave that one away: what they could not find was their own name. A DOS program's environment block ends with a count word and then the full path it was started from, and there was no environment block — so they now get one, and open themselves.

Two of those menus are not read the same way twice

The last two lines above are the ones that took the reader apart. A menu laid out as (G)ravis / (O)thers / (N)one puts the selector inside the word, so the label reads as one — which means neither yes nor no — and puts the whole menu on one line, where a scanner anchored on line starts and double spaces sees only the first option. And a silent option does not have to say "none": Just kidding! I don't even own a GUS!!! is the same answer in a different voice.

Then there is how the key gets in

Reading the menu correctly is no use if nothing delivers the answer, and these programs read the keyboard three different ways.

The polled read. INT 16h AH=01h asks "is anyone there", and it deliberately never manufactured a key: a demo checks that once a frame to decide whether to quit, and would be told yes on its first frame. It answers now, but only on a text screen the menu reader recognises — over its own graphics a demo is still told the keyboard is empty.

The port. BTW.EXE sat on its menu having made zero INT 16h calls in eleven million dispatches, because it hooks nothing and asks the BIOS nothing: it reads port 60h directly, and that port returned a constant zero. It serves the same queue now, make code then break code, and IRQ1 is delivered to a program that installed its own INT 9.

The command line. Some programs name their own way past the screen they are stuck on. AMBIENT.EXE prints MIDAS Error: NO GUS FOUND... USE "AMBIENT /NO_SND" FOR SILENT MODE and means every word: the PSP command tail is populated now, the sweep reads the switch off the screen and retries with it, and the demo renders. Lower-cased on the way in — the message shouts, and MIDAS's option parser is case sensitive.

The detector that was calling working programs hung

The single biggest cause was not a menu at all. A run is declared hung after two hundred handbacks at one address with nothing new on the console — and a loop that stores into a paragraph some compiled region decoded hands control back on every iteration, at the same address, with nothing to show for it. That is indistinguishable from a spin by address alone. IHANMUU.EXE was cut off after 0.5M of its 30M dispatches inside a loop whose SI and BP were advancing the whole time; with the registers folded into the progress test it runs to a full mode 13h screen.

Between them these moved thirteen programs from a text screen to a picture, five from a blank one, and two from no capture at all: 83 graphics tiles became 107.

What is left is a different machine

twelve programs, one blocker, and it is not an instruction either

Thirteen programs got worse looking in this round, and the change is honest. They are the ones that printed Extended memory allocation failure. (weird eh???) and exited; with a lock that works they no longer print anything, and stop a few instructions later at LGDT and MOV CR0, EAX. All thirteen are the same 32-bit DOS extender, and one more — COCAHOLC.EXE — reaches the same place through INT 2Fh AX=1687, the DPMI entry point. An error message is a better picture than a black screen, but it was a message about the wrong thing.

What they want is a descriptor table, a segment whose base comes out of it instead of out of a shift by four, and a code segment whose default operand size is 32 bits. That is not an instruction the decoder is missing. It is a second addressing mode for the whole machine, and it is the largest single item left in the corpus.

Half the corpus was never running its own code

what a compiled region gets wrong about a program that writes itself

The compiler here decodes a whole reachable subgraph at once, ahead of the guest: from an entry point it follows every branch it can resolve and emits the lot into the arena. That is what makes it fast, and it is exactly wrong for the way this corpus ships. Nearly all of it is compressed — LZEXE, PKLITE, DIET — so the file on disk is a few hundred bytes of depacker and a blob, and the program that eventually runs is one the depacker wrote. Decoding ahead of the guest means decoding those addresses while they still hold the depacker's bytes.

uman.com is the clean case. It copies 324 bytes of itself to the top of its segment, far-jumps there, unpacks a screen back over the addresses it came from, and jumps home. The compiled form of "home" was still the depacker, so it depacked again, and again: ten million dispatches executing its own text screen as instructions. Nothing about that looks like a packer bug from the outside. It looks like a demo that drew nothing.

One bit per sixteen bytes

Every store in this VM already funnels through one helper, because unchained VGA needs a decision point. So the fix rides along there: a bitmap marks every paragraph a compile decoded, the store helper tests the bit, and a hit sets a flag. The host then throws away every compiled region and decodes again from memory as it now is — which costs nothing in the steady state, because a packed program unpacks once.

And then it kept running the bytes anyway

Setting the flag was only half of it. Nothing acted on it until the next handback, and a block that falls straight through into the code it just wrote never hands back. A depacker that reaches its payload by far jump was fine, because a far jump leaves the arena on its own; one that simply runs off the end of its own last instruction into the freshly written bytes carried on executing the trace compiled from what used to be there.

The flag cannot cut the block it fires in. Expiry can land mid-x86 instruction, and a resume goes to the last block head, so cutting there would re-run the store. The cut belongs one step later, at the first block boundary after it: the guest address to resume at has just been written down, so refusing the compiled successor is both correct and free.

Five programs — COROMER, rage, ANARCHY, ASM95ZEA, BBUUMI — had been ending up at 0000:003b, executing the interrupt vector table as instructions, for exactly this reason. They ran a decryption stage, fell through into it, and jumped through a pointer the stale trace had left in the wrong register. All five now run their own code.

The other thing a DOS program does is start another program

EXEC, TSRs, and where a child actually goes

CATWALK.EXE ran to completion, exited zero, and drew nothing — a program whose entire job is to start a different one. It carries four files in its tail: an info file, a music module, a player and the demo. INT 21h AH=3Ch, create-file, was not implemented, so each create returned a failure code that the program used as a handle, and the write call accepted it and reported the bytes written. It unpacked its whole payload into nowhere and asked DOS to run it.

Created files now live in memory — nothing here writes the host disk — and are re-openable by name, seekable and growable. AH=4Bh loads and runs one, with its own PSP, its own command tail and a stack of parent contexts to return through. Getting where the child goes right took one correction worth keeping: a loader stub declares it owns all of memory and is expected to shrink itself first, so the child is placed above the parent's minimum allocation — image plus the paragraphs its header asks for, which is where its BSS and stack live. Using the image size alone dropped the player onto the parent's stack, and the parent came back from the call into rubbish.

CATWALK now unpacks itself, starts CapaS3M with CATWALK.S3M on its command line, gets told there is no Gravis UltraSound, and runs the 58KB demo it extracted. That last dependency is real hardware and stays unmet — but the run is now stopped by the machine it wants, not by a call that was never written.

Photographing the page that is on screen

Text mode has eight pages in B800, and a demo animates by drawing into the one that is not being shown and then pointing the CRTC's start address at it. The console model was pinned to page zero, so ant1.exe wrote a full screen and was photographed blank — with the summary line saying, in plain sight, crtc says start=2000. Two thousand words is four thousand bytes, which is page one.

Seven ways to run the same x86

four dispatch shells and three JIT tiers, measured on these demos

The emulator behind every screenshot on this page is a threaded interpreter: each guest instruction is decoded once into a (handler index, operand) pair, and running the program means walking that array and jumping to each handler in turn. How the jump is written is not fixed — tools/toyvm/emit.js emits the same handlers behind four different dispatch shells, and tools/toyvm/trace-jit.js can compile a hot trace out of the loop entirely. The demos in this gallery are what all seven were measured on, which is the reason to describe them here: these are not synthetic loops, they are the exact programs above.

The four dispatch shells

Same decoder, same handler bodies, same guest state. The only thing that changes is the shape of the branch that gets from one handler to the next, and therefore how many distinct indirect-branch sites the CPU's predictor sees.

shellhow the jump is written branch sitesgeomean
tailcall handlers end in return_call $next; one shared $next does the return_call_indirect 1baseline
repl_tailcall that dispatch sequence inlined into every handler's tail, so each opcode re-dispatches from its own site N+10.6%
switch one giant br_table with every handler body inlined as an arm 1+4.2%
calls call_indirect in a loop; handlers return into it 1−3.8%

Replication wins on all ten programs it was measured over, and it is the shell the synthetic microbench never tested. Giving each handler its own return_call_indirect hands the branch predictor a separate history slot per predecessor opcode — and in a real instruction stream the next opcode correlates strongly with the current one. One shared site throws that correlation away. Three independent 94-program sweeps put it at +9.7%, +9.9% and +10.5%; on the programs that draw pixels it is +11.3%, on the ones that do not, +10.0%. It is the rare change that is uniform across a corpus.

The giant br_table does not reproduce its microbench win. A synthetic benchmark claimed +46–49% for the same pair; the demos give +4.2%, and bimodally rather than merely smaller — DSTNFO.EXE +40.1%, COPPER.EXE −26.0%, reproduced across two runs at different box loads. A switch build inlines every handler body into one function, so what it costs depends on whether that program's hot handlers still fit the engine's compilation budgets. That is a property of the program, not of dispatch. calls is the least surprising line: an extra return edge per dispatch buys nothing.

Read the spread before reading any of this. Within-arm min-to-max ran 6–63% across these runs — routinely wider than the gap between two arms. The harness interleaves the arms, rotates which one starts, quotes minima and prints load average either side, because a sequential arm-then-arm layout on this box would have produced a confident number for whichever arm happened to run during a quiet minute.

The three JIT tiers

Dispatch is only the outer loop. The other question is what happens if a hot trace stops being an array walk at all and becomes one wasm function.

tierwhat it is what it removesvs. tier 0
0the threaded interpreter, exactly as shipped—1.00x
1the trace's handler bodies stitched into one function, operands folded to constants dispatch, the operand load, the $ip advance1.83x
2three optimization passes over tier 1 constant propagation, register-file folding, dead flags3.22x

Tier 1 is a text substitution and needs no per-handler work: every handler's operand preamble is generated by one function and therefore has one exact shape, so the stitcher can fold it mechanically. Tier 2 needs the whole trace in view and cannot be done by a stitcher. Folding the operand load is not folding the operand — bodies read it back as a local, which keeps the register-file br_table opaque. Propagating the constant into its uses is what turns an 8-way br_table over globals into a single global access, and only then is it visible that a flag word gets overwritten before anything reads it.

Stitching is most of the distance but not the project. A 1.76x still sitting on top of it after three passes is too large to leave in a stitcher-only design — and that 1.76x is a floor, not a ceiling: tier 2 does no register allocation, so guest registers still live in globals rather than in wasm locals across the trace. That is the single biggest thing still on the table.

One result goes the other way, and it is the reason to measure on demos instead of on theory: only 3 of DRAGON.EXE's 20 flag computations were dead. In a branch-dense bit-reader the flags are genuinely live, so eager flags cost far less on that shape than the theory predicts, and FLY.EXE is a program where tier 2 came out slower than tier 1.

The 3.22x figure counts 23 distinct traces. An earlier 34-trace run read 3.31x, but that set counts one LZEXE/PKLITE bit-reader loop eight times — the same three instructions (d1 ed / 4a / 74) reached through eight different unpackers. Weighting a corpus by how many demos shipped with the same unpacker measures the packer, not the JIT.
